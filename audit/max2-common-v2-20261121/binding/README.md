# New common-goal native inquiry binding

This is source preparation only. No new goal, campaign, old v1 sender, database migration, live webhook, provider upload or production activation is performed by these fixtures.

The actual MAX request must carry the already installed nonempty webhook secret. The optional entry observer accepts only a new receipt returned after the existing canonical post-entry transaction. The optional message observer runs after the existing handler returns normally and verifies the exact persisted external message ID, positive sender ID, customer channel and conversation. It stores reference IDs and hashes in the new private frame table, never request text or initData.

Frames use recursive canonical JSON hashing, so MySQL JSON whitespace/key ordering cannot change the digest. The message freezes a bounded native post-entry set: two entries remain ambiguous. The current canonical registry explicitly writes both post-entry timestamps using gmdate; the runtime adapter must pin its exact SHA256 `590fcda66c13b5c0d89b021dc25e761ef316b8cfdb4b28fedf833f8593d5da0f` before admitting that UTC window. This is not a claim that all historical app DATETIME columns are UTC.

The later projection requires the exact saved substantive inquiry and its authenticated native message frame. It then uses the new signed complete actor-reserve lookup, checks the new ledger's receipt claim, and rechecks the exact selected tracker primary key. It never picks a latest actor/entry/CID. Native Telegram inquiries can use that reader when no linked MAX customer channel exists. Cross-channel ambiguity remains HOLD. Neither branch treats an unavailable lookup as zero. The fixed v1 model and old financial accounting are not modified.
