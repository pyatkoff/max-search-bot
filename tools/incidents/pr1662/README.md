## Что можно проверить сейчас

`partial-install-evidence.cjs` принимает адаптер с двумя доступами на чтение — `get` для REST API этого репозитория и `jobLog` для журналов двух исходных заданий. Он проверяет привязку PR и занятой записи, точный состав запусков, исходные журналы, предыдущий принятый выпуск и результат независимого HEAD. Его единственный успешный ответ сохраняет состояние HOLD. Материалы журналов в PR отсутствуют.

`deploy.proposed.patch` содержит предложение для одного прямого преемника #1662. После допуска оно повторно проверяет публичный статус и SHA чистого рабочего дерева на сервере, пропускает сборку и синхронизацию, затем использует четыре существующие команды — миграции, сверку webhook, установку cron и применение профиля со снимком. Далее предполагаются штатные smoke-проверки и проверка снимка. Производственный SSH в локальном тесте заменён изолированной заглушкой.

В корне клона с историей исходного коммита доступны проверки предложения. Нужны Node.js, Python 3, PyYAML, Bash, Git и patch.

```sh
node --test tools/incidents/pr1662/partial-install-evidence.portable-test.cjs
python3 tools/incidents/pr1662/review_workflow.py
```

## Что должен решить владелец выпуска

1. Подтвердить способ однократного допуска прямого преемника именно исходной попытки и исходной записи #1122. Историческая проверка закреплена за текущим main. При допуске будущего преемника придётся отдельно проверить его родителей, точный набор изменённых файлов, актуальную рабочую копию, право на ту же запись и состояние до первой команды с записью.
2. Определить способ регистрации подлинных результатов двух запусков. Исходный установщик сохраняет результат failure. Для нового запуска сборка и синхронизация имеют результат skipped. Вывод о рабочем SHA опирается на исходный журнал и живую сверку. Последующие четыре действия, smoke-проверки и зависимые работы требуют собственных успешных результатов.
3. До активации связать с этим единственным случаем планировщик, приёмку статуса, проверку потребителями и закрытие записи. В текущей процедуре повтор установщика блокируется на второй попытке. Обычный новый deploy затрагивает уже выполненную установку. Имеющиеся виды квитанций не описывают это исполнение. Одного применения предлагаемого патча недостаточно.
4. После ревью в случае согласованной реализации проверить положительный путь и отказы при чужом SHA, владельце, запуске, неполной проверке либо изменившемся сервере. При частичном исполнении нового продолжения первоначальный допуск повторно использовать нельзя. До получения действительной терминальной квитанции запись выпуска остаётся занятой.
