# Finite saved-finance roadmap phase

The original DEVELOPMENT control pair and its consumed permission remain archived.
The same minute CLI can admit one new, explicitly reviewed finite phase through
`development_work_roadmap_admit`, requiring fresh DEV and forecast scopes.

The real tasks are verification of a new saved repair receipt and verification of
its final saved processing. The second task is materialized only inside the first
acceptance transaction and binds its exact immutable accepted ledger receipt.
Each candidate needs a distinct completed stateless review on a later minute.
The handler uses the canonical read-only financial reader and does not send, poll,
run source audits, dispatch a native owner, edit code or deploy.

Admission pins the exact archive, caller, installed source/schema descriptor and
private reviewed financial capsule. Financial installation evidence remains an
independently verified owner attestation; hashes are not workflow/install proof.
The installation cutoff and new phase admission clock are separate. Old terminal
receipts and excluded original cases cannot be reused as new results.

The new phase permits at most 60 saved reads, 2 original review calls and 3600
seconds from its actual admission. Every review reserves the full 16384-token
and USD 1 ceiling, independently of the consumed old four calls. These amounts
are reservation ceilings, not invoices. No timeout renews the phase.
Waiting evidence consumes no review call. A final failure blocks; an unknown
original read or review remains held without redispatch or automatic refund.

Original request/response/result/readback bytes are retained in binary columns
and returned privately once in structured content with a short digest summary.
The fixed cohort, assigned advertising values, later profiles, original terminal
receipts and individual visit linkage remain distinct. Assigned value is not
actual income. No raw operational capsule belongs in this public repository.

Source preparation, passing CI, installation, explicit phase admission and
observed real cron acceptance are separate evidence steps. This document alone
does not authorize or prove any of them. General coding/deploy/native-owner tasks
remain unsupported until their genuine execution route is available.
