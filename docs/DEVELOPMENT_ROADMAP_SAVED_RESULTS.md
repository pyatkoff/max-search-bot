# Roadmap saved-result adapter preparation

Status: inert preparation. No roadmap admission or runtime integration exists in
this package. The finite commissioning pair, original attempts and spent budget
are unchanged. No new timer, endpoint, model request or native actor is created.

The canonical DEVELOPMENT queue has an accepted finite technical pair. Its old
execution profile is not a coding/deployment permission. A real roadmap extension
needs a separate sealed manifest, current authenticated authority, an auditable
checkpoint, genuine task kinds, original saved results, independently reviewed
acceptance and a bounded ordinary-cron transition. None of those permissions is
inherited from the commissioning pair.

This code prepares exactly two SELECT-only business-evidence adapters:

- saved_finance_new_receipts reads the existing financial delivery projection,
  verifies the privately pinned full cohort/membership, preserves its original
  terminal receipts, excludes separately retained original cases and identifies
  genuinely later saved API receipts.
- saved_finance_processing consumes the exact first result and checks only those
  actual saved receipts for final PROCESSED status. LINKAGE_FAILURE is blocked;
  a pending upload remains waiting. Processing never implies individual visit
  linkage or actual revenue.

Both use ModeledConversionValueDeliveryReader, its existing scopes and shared
five-second/64-KiB budget. They take one read-only repeatable-read transaction,
close only that owned transaction, and repeat authorization. There is no source
transcript fetch, Metrika/source HTTP, provider poll, upload or business write.
A snapshot must match the privately reviewed capsule, including the actual row
roster digest; counts or a hash supplied by a model alone do not prove membership.

Candidates are labelled as evidence requiring a distinct review and a supported
admission. They never accept a task, send a callback, release a claim or advance
the queue. The later queue transaction must load its accepted parent from the
real immutable ledger and pin the result hash; an arbitrary supplied result is
not an accepted parent.

Coding, deployment, HOTEL research, financial sending and native-owner dispatch
are unsupported execution kinds here. They stay explicitly blocked instead of
being mapped to a report or a copied owner ID. Existing operations must be
adopted only from their actual original owner/run/terminal evidence; this
preparation does not reissue them.

Before any activation, the completed control archive and same-admin current
authority need a supported fresh readback. Independently review a concrete
private manifest, genuine route, acceptance, once/dependency rules and separate
finite read/model budgets. An absent host API is not repaired by a local
heartbeat, a guessed callback, a new actor or another account refresh.

The synthetic regression is integrated into the existing queue runner. It covers
new-versus-old/excluded receipts, actual integer-valued decimal aggregates,
parent binding, pending versus final processing, linkage failures, changed
membership/value/old receipts, duplicate receipts/events, incomplete snapshots,
clock bounds, rejected authority and preservation of a foreign transaction.
CI execution and installation must be reported separately from this source.

## Evidence clocks and failure precedence

The private capsule separates api_observed_not_before_unix (the independently
proven original financial installation boundary) from verification_not_before_unix
(the later roadmap verification boundary). A genuinely new financial receipt
observed between those boundaries must not disappear when the adapter is installed.
R1 reports a new terminal failure explicitly. R2 validates every parent target
binding before it examines statuses; any terminal failure outranks another pending
target, independently of target ordering. An absent receipt remains waiting.

The nonempty integration uses the existing populated SQL frontier fixture, shared
with the canonical forecast regression. It executes the real saved-data reader,
then evaluates a new receipt and its later processing, reconciles the separate
later profile and proves unchanged business rows/closed read-only transactions.
No live financial identities, timestamps, API response or private capsule is used.
