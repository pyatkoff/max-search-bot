# Finite DEV server control pair

This opt-in mode runs two bounded technical reports through the **existing minute
DEVELOPMENT cron**. It is not a coding agent, a native/durable host session, a
deployment executor, or proof that the whole development roadmap is automated.
Existing native DEV queues, HOTEL data/keys/allowances, manager replies and customer
operations are not moved into this mode.

## Explicit admission and identity

The sole supported read route remains
`development_work_status({queue_id:"DEVELOPMENT-CONTROL-20261028"})`.
It returns a server-generated candidate only when the exact old A01 metadata is
retired BLOCKED, with one task/one retirement/no worker receipts and no current WIP.
Reading it creates nothing and sends nothing.

Appending **exactly the single A02 spec and expected/new plan hashes from that
fresh candidate** is an explicit ARM of this finite mode. It reserves authority
for at most four original future ordinary-cron sends under the frozen policy:
A02 producer, A02 stateless reviewer, B producer, B stateless reviewer. The append
itself sends no request and creates no B task/input hash/outbox. An ordinary
append, guessed hashes, a precreated B row, another queue or a copied native claim
does not grant this authority. The historical native queue owner remains unchanged. This new pair may bind the
actual existing same-admin DEV connection as its separate immutable execution
authorizer; callers cannot select that connection in tool arguments or claim a
native HOST identity.

The candidate pins the actual installed code-file hashes, schema and required
unique indexes, current configured transport profile, templates/instructions,
legacy baseline, distinct logical author/reviewer and finite policy. The public
source defaults (one hour; four calls; 16384 total tokens reserved per call;
1000000 USD_micro reserved per call) are **proposed policy ceilings**, not evidence
of a live operational authorization, a provider tariff, an invoice or actual
spend. Before real ARM, the existing coordinator must independently accept the
installed candidate and its actual applicability, budget, deadline, owner and
baseline. Old A01/76 configuration UNKNOWN, old factory UNKNOWN and their spent
budgets are not reconciled, retried, refunded or reassigned by this code.

## Narrow admission authority overlay

The original q.oauth_connection_id, A01 bytes, retirement and completed handoff
remain unchanged. This does not repeat their consumed operation or inherit old
execution permission. Only this fixed eligible unstarted server pair may use the
actual current same-admin/project DEV connection: the backend positively verifies
both historical grant metadata and the active current canonical grant. No secret,
credential, new account/grant/consent, changed administrator or queue discovery is
involved. Canonical supported scope names/order/reply-pair checks remain exact;
the scope byte bound is derived from the actual resource scope catalogue
(including a valid 152-byte legacy profile), not a guessed 100-byte maximum.

Only existing status and exact A-only append use this route. Native create,
ordinary append, claim/started/complete/resolve/retire/handoff/subscription powers
do not widen. The candidate pins the backend's actual current execution authorizer
and the frozen native owner; a copied candidate from another connection cannot
authorize ARM. These private identities are not hard-coded into public source or
chosen by caller arguments. The uninstalled096 sidecar stores the independent
execution connection and its immutable binding. A lane/queue transaction, plan
CAS and unique control row permit one ARM in an old-owner/current-authorizer race.

After binding, status is limited to the historical native owner or the exact
bound execution authorizer, with fresh positive authority for the overlay. A third
same-admin connection cannot read/rebind it. The runtime uses the sidecar
authorizer. Before every send and acceptance it checks an active current authority:
assertCurrent for native-owner mode, assertPair for the overlay. Revocation during
a provider call preserves the original observations in UNKNOWN, without acceptance,
B materialization, refund or resend. Historical same-admin metadata alone never
permits server execution.

## Existing cron only

`tools/development_work.php tick` first checks for this explicit binding.
Only the installed entry with DEVELOPMENT_WORK_TRIGGER=cron may dispatch. No new
timer, endpoint, user-facing tool, manual tick, model callback or acceptance tail
starts a send. The existing DEV OAuth owner is freshly authorized. A binding
causes the CLI to handle this queue exclusively; it never falls through to native
callback dispatch on a hold or failure. Native mode alone continues to use its
existing signed pending delivery.

The canonical DEVELOPMENT lane and queue serialize preparation. Inside one SQL
transaction the server records the immutable job index, exact **actual wire body**
and its digest, ordinary cron identity/minute slot, retained claim, UNKNOWN attempt
and full token/money reservation. It commits before one transport call and holds
no SQL locks over the network. There is no resend, provider/session/model fallback,
refund, age-based release, second owner or public bypass. SQL unique constraints
cover response IDs globally, queue/task/role, and queue/minute slot.

A missing response, timeout, lost commit acknowledgement, duplicate ID, incomplete
response, refusal, invalid report, oversized output or expired deadline retains
UNKNOWN and the original reservation. A later tick is observation only. An
unconfigured provider or policy/schema drift holds without a send. Manual
invocations cannot create model execution evidence.

## Actual evidence and acceptance

The model receives frozen static input separately from bounded actual named
evidence: installed runtime/schema digest projection, binding/spec/plan, actual
ordinary cron/outbox identity, configured profile/reservations/deadline, and old
queue baseline-versus-observed hash with its explicit limited coverage. B also
receives the actual accepted A receipt/result/review/readback hashes and original
producer/reviewer response and cron IDs. Each check has one exact supporting
reference; absent or foreign references are rejected. No producer input contains
its own future response/result/review/acceptance IDs.

The original HTTPS transport supplies response ID, completed/incomplete status,
model, usage, HTTP status and capture completeness. Model JSON cannot choose these
fields. These observations are retained before report acceptance, including known
rejected/incomplete/late outcomes. A separate stateless reviewer invocation sees
the exact saved candidate and original producer transport evidence; it is not
reported as a native ROOT chat turn.

DEV request/response capture is at most 8192 bytes each and normalized reports at
most 2048 bytes. Overflow stops capture and marks the retained prefix incomplete;
it never earns acceptance or a new call. The same supported status route returns
all retained job/request/actual-mismatch/response/report bytes as base64 with
digests and original observation metadata. Incomplete retained bytes are explicitly
labelled; they are never described as complete original output. No headers,
credentials, customer or hotel content is included.

Both actual MCP wrappers bound DEV-status string RPC IDs to 1024 bytes before
authorization or errors, and bound the complete duplicated text + structuredContent
JSON-RPC result to 262144 bytes (including escaping). The internal proof budget
reserves status/envelope room; an oversized proof fails closed rather than clipping
it into an acceptance. There are no unsupported paging parameters or new methods
that depend on catalogue refresh.

Acceptance requires the exact immutable original request, independent raw response
parsing, real completed metadata and bounded usage, deterministic evidence pins,
valid candidate and distinct reviewer response/cron identities, full supported
readback and a still-open frozen deadline. No actual code/CI/deploy or native HOST
credit can be inferred from these technical JSON reports.

A02 acceptance, accepted ledger, released own claim, resolution of actual B input
and spec, new plan CAS and the single B pending row commit **atomically**. B starts
only on a different, later ordinary cron invocation/minute slot. A lost result
commit cannot leave a successful A acceptance without its dependent admission.

After B acceptance, the truthful existing queue is:
tasks=3, retired=1, blocked=1, accepted=2, worker_receipts=2, current=NULL,
overall state=BLOCKED; server control state=complete, four calls spent, no owned
claim/run/WIP. Retired A01 is never counted as accepted or changed to COMPLETE.
Future ticks make no fifth send.
