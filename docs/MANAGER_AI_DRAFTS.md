# Manager AI reply drafts

An assigned manager sees an available AI reply beside an empty composer, with
`Tab — вставить` and an equivalent button. Tab applies only while that composer
has focus, without modifiers or composition; an existing reply is never replaced.
The full preview retains the reason and checks. Accepting a prepared suggestion
explicitly loads `prepared` to record its provenance, then uses the existing fresh
`validate` and canonical composer insertion. It never sends the reply.

Manager2 observes the selected reply-owned conversation's ready cache and, for
the existing workspace administrator with fresh `owner_read`, accessible foreign
conversations too. Reads run every 15 seconds for at most ten minutes per
context/visible period. Hidden tabs, navigation, account changes and access loss
cancel the observer. `prepared_status` returns metadata; `prepared_preview` reads
the full current proposal without recording feedback, returning `draft_id: null`
and no job identity. Both retain canonical auth, CSRF, fresh session/context,
ownership and expiry checks. Passive reads never call a provider, read a selection
page or mark messages read. A cache miss stays quiet; generation still requires
an explicit AI or regenerate click. Expiry clears the suggestion and ready button
independently of the bounded observer.

The Manager2 composer says `AI — Ответ готов` for an available draft: green for
an automatically prepared reply, blue for a result generated by explicit click.
Hover/accessible labels explain the source and Moscow time. Results without a
customer draft say `AI — Рекомендации` and do not announce a ready reply.
Inline suggestions do not open the full preview or move focus. In foreign chats,
the owner sees the responsible manager and `Только просмотр`, without insertion
controls or foreign feedback. Ordinary employee supervisors retain explicit AI
opening. The personal setting `ai_ready_notice` (`show`/`hide`, default `show`)
hides both inline suggestions and the quiet readiness notice. It uses existing account
preferences, version checks and operation receipts; old JSON rows receive the
default at read time without a migration or write. The AI button remains usable.
Sending remains the existing manager action. The owner-authorized ChatGPT worker
is documented in [prepared replies](MANAGER_PREPARED_REPLIES.md).

## Owners and boundaries

- `manager/ai-draft.php`: canonical ManagerHttp authentication, CSRF and JSON
  boundary; `generate`, `prepared`, `prepared_status`, `prepared_preview` and
  `validate` actions.
- `ManagerAiDraftContextService`: fresh active-account, project/source visibility
  and strict reply ownership; short read-only snapshots; revision fingerprint.
- `ManagerAiDraftService`: isolated draft instructions and strict result checks.
- `ManagerCompanyKnowledge`: immutable approved company snapshot, versioned source
  and expiry checks; see [company knowledge](COMPANY_KNOWLEDGE.md).
- `ManagerSelectionSnapshot`: bounded on-click observation of supported selection
  links, source-message binding and explicit unknowns; see [selection context](MANAGER_SELECTION_CONTEXT.md).
- `ai/ManagerDraftClient.php`: fixed OpenAI Responses endpoint, existing
  `OPENAI_API_KEY`, feature-specific model/reasoning/tier, strict JSON schema, `store:false`, no tools,
  no redirects, bounded response and a 20-second timeout. No automatic retries.
- `workspace-v2-ai-draft.js`: preview, stale-result fencing and explicit insertion
  through `WorkspaceV2Conversation.insertAiDraft`; no new send implementation.

The owner-directed profile from 19 October 2026 is `gpt-6.1-sol`, explicit
`reasoning: {effort: "low"}` and Standard `service_tier: "default"`, for both
the manager draft and shared MAX/Telegram/website bot transport. Draft overrides
`MANAGER_AI_DRAFT_MODEL`, `MANAGER_AI_DRAFT_REASONING` and
`MANAGER_AI_DRAFT_SERVICE_TIER` stay feature-specific; `OPENAI_MODEL` affects
only the bot. Canonical deployment reconciles these four external configuration
literals and verifies the effective request bodies without provider calls.
See [AI model rollout](AI_MODEL_PROFILE.md). No sampling parameters are sent.

The model supports draft efforts `low`, `medium`, `high`, `xhigh`, `max`.
Malformed settings fail closed. Explicit optional draft tiers `fast`/`priority`
remain supported for future separately authorized configuration, but are not
selected by the production rollout. Provider-served tier and latency are not
inferred from the requested tier. Historical Fast tests remain historical;
the existing 20-second timeout and token/byte limits are unchanged.

For isolated evaluation, `requestJson()` and the pure `parseResponse()` accept
an optional third callable. After a completed assistant JSON object is decoded,
it receives only the provider's bounded model name, allowlisted served tier and
nonnegative integer token counts (up to 10,000,000). Missing or invalid model/tier
remain `null`; invalid usage fields are omitted, never inferred from the request.
Only input/output/total tokens, cached input tokens and reasoning output tokens
are projected. No response IDs, instructions, content, raw body or arbitrary
metadata reach this observer. It is not invoked on errors, refusals or incomplete
responses; observer exceptions do not change the result. No observer is installed
in the manager endpoint, and this client does not log or persist the metadata.
The eight-field manager result remains unchanged; its schema and evidence checks
still run separately after decoding.

The normal project initializer has a legacy UPSERT. This endpoint invokes
`ProjectAccessService::initializeReadOnly()` before auth instead. Draft generation
does not call the HTTP `detail` action, mark messages read, update needs, take or
release conversations, create tasks, or invoke bot delivery/state services.
Admin edit permission does not allow drafting replies for another manager.

Each context contains at most 120 recent messages and 40,000 Unicode characters.
Older history, truncated text and unread attachments/selection links are explicit.
The model receives only the projected conversation: external identities, raw
metadata, media URLs, phone numbers and email addresses are excluded/redacted.
Selection observations add at most about 12,000 Unicode characters through a
server-only reader outside DB/session locks. Raw page URLs/HTML do not reach the
provider, and `validate` never refetches them. Names and other personal content can still occur in message text; the payload
is private and must not be logged or committed.

The source fingerprint includes edits in place and ownership/status, not only
the latest message ID. The initial transaction ends and session lock is released
before the provider call. Afterwards the endpoint reloads the session and reads
a new authorized snapshot. New messages, edits, revoked access, reassignment,
closure, delivery suspension, account changes or CSRF rotation invalidate the
result. A separate fresh `validate` precedes insertion. These are read-time checks,
not a reservation; the existing send path remains authoritative at send time.

## Working constructor variants

The existing authorized read snapshot may also read the current persisted
constructor draft through `ManagerTourSelectionReferenceContext`: one bounded
primary-key SELECT, no page/provider call or write. Only normalized included
AnyTour variants reach `working_selection`. It is a manager's editable working
set, not a tourist preference, proof of sending, current-trip criteria or a
verified fare. Excluded variants, draft/offer IDs, private URLs, raw source keys
and photo bytes are not projected. Phone/email text uses the shared redactor;
other personal text may remain in free-form notes, as in the authorized transcript.
Photos remain explicitly unread.
Original normalized supplier conditions stay separate from manager changes;
their differing fields are listed rather than silently promoted to source facts.

The whole group and its actual encoded request increment, including conditional
instructions, must fit32KiB and the existing196608-byte text envelope. Admission
is last, after all existing transcript/company/post/route/selection/photo/hotel
evidence. Overflow omits the whole optional group without shortening that
baseline. Empty, invalid, unsupported or unavailable drafts leave the old input
and base instructions unchanged; absence is unknown, not proof of no offers.
Version, exact stored-content hash and policy revision participate in the existing
manual/preparation stale checks, without a continuously changing capture time.
Posted fields cannot populate this server-owned evidence.

Both explicit generation and private preparation use the same input. With useful
matching variants, the helper can compare supported conditions, the in-budget
choice and a justified10–20% alternative; it must preserve actual request scope,
source age, unverified costs and material unknowns. This is candidate-context
delivery, not automatic live search, ranking accuracy, constructor mutation or
independent proof of model quality. Native collector/use and fresh real reply
acceptance remain separate; the regression uses only synthetic data and a spy.
The working draft alone never triggers contact. For an open current comparison,
new supported variants may fulfill the manager's earlier comparison promise;
that promise is not a reason to suppress the actual substantive comparison.
Stop/purchase and price-verification boundaries remain unchanged.

## Knowledge and output

Generalized communication procedures and approved project-specific company facts
have separate owners. The company catalog initially contains only the AnyTour
public name and search website from the versioned project configuration. It does
not approve office, contact, booking, payment or document conditions. Private pilot
examples and candidate company/personal knowledge remain outside the active base.
Personal knowledge must be scoped to its actual author; current conversation
ownership is not authorship.

Archive-derived procedural learning is a versioned instruction change, not
weight fine-tuning or automatic ingestion of historical replies. The draft
instructions preserve the bot's existing whole-party budget default unless the
customer explicitly gives a per-person amount; genuine ambiguity between
families/rooms still needs clarification. They distinguish service type, room
plans, actual travellers versus tariff labels, days versus nights and arrival
deadlines. Forwarded posts do not establish the speaker's personal authorship,
customer agreement or current offer facts.

When a question depends on an already supplied attachment or selection, the
manager should inspect it before asking the customer to repeat the same data.
Unread old media must not block an unrelated answer. Neither the customer draft
nor the internal reason may claim that unread media were inspected or contain a
particular document. AI limitations stay in reason/checks, not in the manager's
voice to the customer; a concrete check can be more useful than an empty promise.
These procedures do not approve company facts, learn an individual manager's
style or establish production accuracy. Validate changes on separate past-only
histories with the same fixed model/profile, distinguishing helpful drafts from
justified abstentions and policy-only results from actual provider calls.

Trip scope applies to internal `reason`/`checks` as well as the customer draft.
A new season or period does not by itself establish that the old duration still
applies, or cancel the earlier request. Keep that relationship unresolved when
the customer has not made it clear. A clear date-only edit of the same trip
preserves its other confirmed requirements; explicit shared conditions apply
only to the named alternatives.

Incompatible ages for the same child and trip remain a source conflict until
the customer clarifies it. A manager's repetition or a tariff label does not
resolve the conflict. Preserve compatible present/travel-date ages, different
children and explicit customer corrections. Resolve the conflict before an
age-dependent calculation, while still answering an independent current question.

Prospective neutral semantic controls for these instruction changes:

| Synthetic situation | Expected boundary |
| --- | --- |
| June Portugal for nine days; separate September Iceland request without duration | Do not transfer the nine days or cancel Portugal. |
| July trip followed by a November-date question with unclear relationship | Preserve uncertainty about the relationship and duration. |
| Customer says it is the same trip and changes only its departure date | Retain other confirmed conditions without asking the whole request again. |
| Customer explicitly applies six nights to both named alternatives | Keep six nights for both, without inventing other unknown conditions. |
| Same child's age is given as five and nine; manager repeats nine | Keep the conflicting evidence until customer clarification. |
| Customer explicitly corrects five to nine for that child and trip | Use the correction, without retaining an obsolete conflict. |
| Child is eight now and explicitly nine on the trip | Do not invent a conflict between compatible ages. |
| Two children are five and nine | Keep the children separate. |
| Age is unresolved but the current question can be answered independently | Give the supported answer and retain the age check for dependent work. |

These are unsubmitted development controls, not measured model results. The
synthetic transport regression checks canonical instruction delivery and the
existing request cap at both context limits; injected replies do not establish
that the model follows these rules. Provider quality and latency require a
separate frozen evaluation; previous results and criteria remain unchanged.

The provider payload receives only eligible server-owned `verified_company_facts`
from the authorized conversation's project. Transcript/context fields cannot
populate this list. Its knowledge revision participates in post-generation and
pre-insert validation. Offline callers without a server snapshot retain an empty
list. A narrow deterministic check of the latest real customer question
about the agency's office/address or a personal visit returns manager checks
without a customer draft or provider call. Prior dialogue claims do not bypass
this boundary. Questions about a hotel's or a consulate's address remain ordinary
conversation analysis. Evaluation records distinguish policy results from actual
model calls.

Model output separates the customer draft from the reason and manager checks.
It can decline a new message after a stop, purchase, thanks without a new
question, or a pending promise to check options. It must not invent prices,
availability, policy, hotel properties, payment details or completed actions.
Schema/evidence validation cannot prove factual correctness: the manager reviews
every draft. Only supported selection links may be read on explicit generation;
attachments/other links stay unread. Current page observations are not send-time
versions and historical offers are not presented as current availability.

`no_contact` is advice about the proposed message, not a status change or a
permanent prohibition. This slice does not implement timed follow-up scoring,
automatic tour selection, weight fine-tuning, personal style learning or autonomous sends.

## Verification

Required synthetic suites exercise context/read-only access, strict provider
results, actual endpoint/session races and canonical composer insertion. Browser
coverage uses the actual PHP shell/assets with synthetic API responses, including
mobile widths and stale authorization. Existing required and visual checks stay
mandatory; a fixture pass does not establish live provider quality.

Private historical evaluation must contain only messages through each cutoff,
without later outcomes or current selection-page contents. Generated results are
reviewed against evidence separately from manually prepared reference replies.
Do not publish plaintext examples, model inputs/outputs, private URLs or credentials
in GitHub, Actions logs or artifacts.

## Older-history presentation and client freshness

The client retains fingerprints of messages captured when a proposal/check
started. Prepending an already-existing older page does not invalidate that
proposal or restart its request. New activity, changes/removal of captured
messages, owner/account/auth/navigation changes still invalidate it. The
canonical server revision is separately validated before insertion, including
history or reference edits the client has not observed. This is not a
latest-message-ID-only freshness contract or an additional cache/send owner.
