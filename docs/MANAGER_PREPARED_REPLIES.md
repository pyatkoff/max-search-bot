# Prepared replies through ChatGPT

The owner's fixed bot demo dialogues are internal work. Background collection and
background-job enqueue/list/context/save/cache reads exclude the exact scoped
identities owned by `InternalOwnerDialogueScope`, including already-issued jobs.
The predicate runs before the candidate limit; it is not a name or message-text
filter. Chats remain visible and their messages, status, ownership and `is_test`
flag are untouched. Explicit manual AI/demo context remains usable.

Opening a manager chat now has a separate `open_chat` demand scope. Migration069
adds its purpose, requesting manager and viewer-access revision to the existing
private preparation queue. The browser's `ensure_prepared` operation authenticates
the current viewer, requires CSRF and exact current message/context, and checks an
active existing ChatGPT subscription. Ordinary managers can request their own
reply context; the workspace owner can request an accessible foreign context in
read-only mode. Employee supervisor grants alone do not enable automatic work.

This bounded selected-chat request can include an old, already answered, internal
demo or owner-accessible archived chat; it does not widen the background collector.
The worker still decides whether a customer reply is appropriate. A no-contact
decision is a completed result, not a reason for a generation loop. Current ready
results are reused. Concurrent requests from the same account/tabs reuse the same
exact-context job; an expired demand may renew as a new immutable job. Requester
bindings deliberately remain separate across accounts.

Pending demand metadata, private context, completion and preview recheck the
requester's account, project/source visibility, owner binding, viewer scope and
canonical context/instruction revision. Loss of access or a changed conversation
invalidates the work. Background deduplication excludes demand jobs. The existing
bounded verification pass retires confirmed obsolete demand jobs through exact
compare-and-set, without renewing them or creating work for an unopened chat.
There is no new cron, model profile, paid model call or send path. The
existing signed event notifies the connected ChatGPT worker immediately after
queuing; the existing minute cron retains delivery retry ownership. Callback
acceptance is not completion: the UI polls for the actual current saved result
and displays preparation or unavailable/delayed status until then.

The owner requested analysis and prepared replies in ChatGPT without separate
model API calls. The first private read-only pilot reviewed seven real conversations:
one clarification draft, three manager checks and three cases needing no new text.
Its evidence and replies remain private. This implementation connects that workflow
to a bounded work queue and the existing manager reply preview.

## Manager behavior

An explicit AI click reuses a useful current prepared reply. A cache miss, cache
outage, or a recommendation requiring further work starts one manual generation
within that same click. A no-contact decision stays explicit and does not trigger
a model call. Passive readiness remains metadata-only and never generates;
automatic selected-chat preparation uses the separate queue request above.
“Другой вариант” / “Повторить подготовку” explicitly generate again.
The preview keeps the customer text separate from internal reasons/checks.
“Добавить в ответ” revalidates the context and appends through the existing composer;
it preserves existing text and files. Nothing sends automatically. Prepared results
have their own provenance and do not impersonate feedback generated by an API call.

## Photo evidence

The canonical authorized snapshot captures private photo capabilities separately
from the textual transcript. Only explicit generation or `get_reply_context`
opens up to four raster images: the saved immutable current post, then recent
customer attachments. MAX and Telegram reuse the protected media owners; no
provider URL, token or file identifier is passed to the model. MAX recovery in
this path does not edit message metadata, so reading a photo cannot invalidate
its own source revision. Session/database locks close before downloads; fresh
ownership, revision and OAuth checks still run afterward.

Manual Responses requests carry actual inline image inputs with high detail.
MCP preparation returns image content blocks alongside the canonical text, with
no duplicate base64 in structured/text context and no image bytes in proposal
storage. `photo_evidence` binds each image index to its message/attachment or
post entry/version. Only fully attached message media loses its unread marker;
unread files, quotes, unavailable bytes and omitted album images remain explicit.
Each image is at most 2 MiB and total image bytes at most 4 MiB. Larger original
images up to 5 MiB may be reduced with GD when available. Invalid, executable or
oversized media is never represented as read. Photos supply source observations,
not verified current prices, availability, booking consent or instructions.

## Queue and freshness

The existing subscription-gated cron selects at most20 **recent unanswered**
customer inputs per pass. Recency means the actual latest genuine customer
message was created within72 hours of capture, not the job's creation timestamp.
Callback/start/bot-started events cannot open work or refresh that age. A human
manager reply suppresses automatic work; an arrived task or an active assignment
alone does not reopen an answered or archived chat. This is an automatic workload
boundary, not a deletion or a claim that an older customer never needs help.
Explicit manual AI and regeneration keep their existing authorized scope and full
history. Empty text does not exclude real voice, photos or other media.

The cheap SQL source gate runs before the candidate limit/full context capture,
and again in enqueue, pending inventory and context/save. Old already-issued jobs
cannot bypass it. The background pending inventory uses one bounded metadata
query. Opened-chat requests have a separate bounded lane and canonical viewer
metadata checks; neither lane hydrates histories/photos or consumes work.
Canonical source/project/owner/delivery
authorization and exact context/instruction fences remain authoritative. Test,
closed, self-service and scoped internal-owner conversations stay excluded;
off-shift active owners and lawful unassigned waiting enquiries remain eligible.

The automatic scan reuses the existing versioned waiting cursor; bounded full
validation retains its verify cursor. Old due/active cursor rows are left alone,
not deleted or repurposed. Compare-and-set still prevents a slower pass rewinding
progress. Neither one pass nor aggregate counters promise complete coverage.

Migration062 adds a nullable private customer-input digest and lookup index to
the existing work table. No transcript is copied and there is no blanket migration
backfill. A legacy ready row with a null digest may learn that auxiliary lookup
hint only after a fresh canonical snapshot exactly matches its original context,
latest-message and instruction revisions, its saved proposal validates byte-for-byte,
and current source/input/owner checks still match. No proposal, provenance, status,
prepared timestamp or preview expiry changes. Unknown or changed legacy evidence
never gets a guessed digest from a message ID or age. The first verified scheduled
pass may still capture that context; later passes skip it before reading history,
including after preview TTL expiry. The digest binds the latest genuine customer's ID, text,
timestamp, channel and attachment/event metadata, separately from full context
and instruction revisions. An unchanged completed decision, including no-contact
and human-check results, remains handled after its one-hour preview TTL or a
route/knowledge/post/instruction refresh. A new message or edit to that latest
input permits new work. A pure later click does not. The collector checks this
small binding before opening a full snapshot. Live unfinished work is also skipped
there; bounded reconciliation still checks its exact canonical source.

Pending work still expires after an hour. Only unfinished expired work may renew
as a new immutable deterministic job. Completed proposals and provenance remain
immutable; expiry never authorizes a stale insertion or another model call.
Normal context/instruction/owner revalidation, idempotent completion and conflicting
completion rejection are unchanged. Reconciliation expires only confirmed obsolete
pending rows through exact-binding compare-and-set, never ready results. Storage
uncertainty is deferred, not treated as proof of staleness. The queue keeps its
200-pending soft cap and existing cron flock. No message, task, assignment, unread
marker, shift, routing, AI profile, budget, send or schedule is changed.

An already-ready unassigned proposal can still be reviewed after lawful take if
the separate evidence digest matches every source message/edit/metadata,
project/source/channel and approved knowledge/reference projection. Current owner
authorization, normal preview expiry and fresh owner-specific insertion revision
remain mandatory. Unfinished pre-take work cannot complete after take.

The worker reads each bounded canonical context separately and uses the exact
server-owned instructions and approved knowledge facts returned with it. Unread
photos and external communication stay unknown. Explicit `get_reply_context`
reuses the manual AI's bounded reader for supported public selection links and
returns only redacted card fields with source-message bindings and observed time.
Failed/unsupported reads remain unknown. Reading happens outside database locks;
current source, owner, job lifetime and requesting OAuth access are rechecked after
it. See `MANAGER_SELECTION_CONTEXT.md` for transport limits and the distinction
between observed page contents and verified current prices. Imported eight-field
proposals are checked through `ManagerAiDraftService` with an injected result, so no
default provider transport is selected. All source status/ownership, source revision,
knowledge and instruction changes invalidate older work. New storage never changes
messages, lead state, ownership, shift, routing or customer contact preferences.

The same canonical snapshot now includes bounded `origin_posts` and
`travel_reference` evidence for AnyTour. The former reuses the saved version bound
to the latest channel-post entry, not the post's later edited version or guessed
start payload; one previous entry is explicitly historical. Unknown latest entries
never fall back to an older post. Text is redacted and capped; attachments remain
unread. A post identifies the enquiry, not consent to book, a personal budget or
verified current conditions. Explicit subsequent customer changes take priority.

Route evidence primarily reads the existing `HotelDatabase` catalogue: active
`catalog_departure_countries` plus the separate `_direct`, `_charter` and
`_direct_charter` matrices, joined to active departure/country names. One bounded
SQL statement observes a consistent set without database, supplier or schedule
writes. The existing Search3 catalogue owner refreshes these tables; this reader
does not install another updater. Up to three explicitly mentioned departures
are kept separately, with catalogue genitive names used for matching. Catalogue
sync age, source, matrix counts, partial coverage and output truncation are explicit.
The matrices have no departure dates (`dates_available=false`); empty dates never
mean no flights. If the catalogue cannot be read, the historical local
`tourvisor_routes.json` reader remains a fallback with its own file age and the
fixed catalogue failure reason. An absent legacy file does not describe the DB.
Older-than-24-hour, unavailable, partial or absent rows never prove that flights
are unavailable. Even a fresh row is not live inventory, price or hotel verification.
These references participate in the context revision, so changed route evidence
invalidates an older prepared reply without transcript changes. The manual generation path receives the same server-owned projection;
caller-supplied reference fields cannot substitute for it. Optional evidence is
omitted rather than exceeding the existing transport size cap.

The response instructions retain unchanged departure city, party, budget and
preferences when a customer corrects a month/date within the same enquiry. They
still separate genuinely independent trips and clarify only an ambiguous link,
not the entire intake. These are prompt rules, not proof of a future model result;
the manager remains the reviewer and sender.

Shared business principles are owned by `TourConsultationPolicy`. Both ordinary
manager drafts and private virtual authors/reviewers consume that same text.
Role-specific sources, company-fact verification, photo/selection handling,
output schemas and permission boundaries remain separate. The complete returned
instructions participate in ordinary and virtual instruction revisions.

Explicit tourist wording takes priority over a publication. A click alone neither
establishes the subject of an enquiry nor justifies a departure/party confirmation;
empty start/click entries remain silent. Use a post only where the message links
the request to it. Preserve known conditions, necessary ambiguities and verified
route coverage. Egypt and Turkish resorts use all-inclusive as a working default;
explicit different meals and city stays such as Istanbul remain distinct.

Synthetic calibration examples, not observed model-quality results:

| Request and source evidence | Next step |
| --- | --- |
| Explicit Lisbon stay; essential conditions known | Prepare the requested selection without an optional city/beach fork. |
| Honeymoon; origin and budget unknown | Use a pair as a working hypothesis and ask only material missing conditions. |

| Explicit Saint Petersburg departure and three adults | Preserve both; no repeated departure or child question. |

These prompt rules do not mutate booking fields or prove future generation quality.
They do not authorize rewriting completed jobs: normal instruction/context revision
freshness and manager review still apply.

The same owner review clarified service intent: an old generic word «билеты»
does not itself establish an air-only enquiry. In the reviewed chronology, an
October 11 question about January prices had no country; on October 19 the
customer entered through an Egypt package post and named Egypt. Continue package
selection in that current context rather than asking package versus tickets solely
because of the old word. Keep the stated January period. Explicit «только
авиабилеты», «без отеля» or «перелёт не нужен» remain authoritative; a substantive
service conflict still warrants clarification. This is contextual interpretation,
not a fixed age cutoff, deletion of history or permission to ignore explicit needs.

## OAuth and private MCP connection

MCP URL: `https://app.anytoour.ru/manager/ai-mcp.php`.

The entire endpoint requires an opaque OAuth access token. Migration 045 isolates
public-client registration, grants, one-use code hashes and access/refresh hashes.
Authorization-code flow requires PKCE S256, exact resource/audience and exact
documented ChatGPT stable redirect. RFC 9207 issuer identification is advertised
and echoed. No API keys or credentials in query URLs are supported.

Only a currently active administrator with membership in the current active project
can consent. The ordinary manager login remains the identity owner. Consent is a
separate explicit CSRF-protected POST bound to a short pending request in that session.
There is no remembered automatic consent. Access tokens expire in one hour; rotating
refresh tokens cannot extend the absolute thirty-day grant. Replay revokes the family.
Every request checks current administrator/project/grant state. The owner can revoke
connections at `/manager/ai-oauth.php?action=connections`; callbacks stop on grant
revocation. No raw credentials, message text, drafts or callback secrets are logged.

Browser authorization failures retain their OAuth error and, for `invalid_request`,
add a fixed `error_description` category. Missing/invalid form decisions, unsupported
encoding, malformed form fields, and malformed/missing/expired session requests are
distinguishable without reflecting request values, account IDs or credentials.
These categories diagnose the failed step; they never imply that consent succeeded
or relax CSRF, the ten-minute pending lifetime, administrator or project checks.
The HTTP regression submits controls parsed from the actual rendered consent HTML;
it is not an owner-session acceptance test. The native Chromium/WebKit fixture clicks
the rendered form over loopback HTTPS with real secure cookies and the exact PHP
endpoint/SQLite service; its fixed ChatGPT callback is intercepted locally. Neither
fixture establishes the owner's live connection or actual ChatGPT code exchange.
The form-navigation CSP allowlist contains only self plus that pinned callback;
scripts/frames/base URLs remain disabled. A native-browser negative control restores
only the former self-only form policy to distinguish redirect blocking and a
subsequent consumed-request rejection from server form parsing. The callback TLS
server and deny-by-default CONNECT proxy are entirely loopback; browser redirects
cannot fall through to the Internet, even if route interception misses them.

Public discovery is limited to authorization/resource metadata. The authorization
issuer is `https://app.anytoour.ru/manager/ai-oauth.php`. RFC 8414 inserts the
well-known segment before that issuer path, giving an explicit PHP discovery URL.
The host denies bare and trailing-slash directory indexes; clients must discover
the issuer-specific PHP route, without relying on a directory index or redirects.
Verify both public metadata routes on the actual host:

- `/.well-known/oauth-authorization-server/manager/ai-oauth.php`
- `/manager/ai-oauth.php?action=resource`

Authorization metadata `issuer`, protected-resource `authorization_servers` and
every callback's RFC 9207 `iss` use that exact path-bearing issuer. The MCP resource
remains `https://app.anytoour.ru/manager/ai-mcp.php`; authorization, token, registration
and revocation action URLs remain under `/manager/ai-oauth.php`.

Installing and authorizing a custom MCP plugin is a separate account action. Code
deployment and cron installation do not establish a ChatGPT connection. After the
owner adds this URL as an OAuth MCP plugin and signs in, discover its actual event
source/schema in ChatGPT and test a harmless queue read before configuring automation.

## Tools and events

Ordinary tool discovery also accepts the handshake-based MCP versions `2024-11-05`,
`2025-03-26`, `2025-06-18` and `2025-11-25`. `initialize` returns the supported
version requested by the client, or the latest supported handshake version for an
unknown version. It must not force `2026-07-28` on an older client: such a client
can reject initialization before `tools/list`, even after successful OAuth.
The handshake advertises tools only; MCP 2.0 Events retain their separate
`server/discover` contract. All discovery still requires current OAuth/admin/project
authorization and never reads or changes queued jobs.

Request-level `_meta` is accepted as a metadata object and removed before method
argument validation. This supports required MCP 2026-07-28 client metadata and
optional metadata from older clients. It is never an authorization source or
forwarded to the preparation store. Tool argument allowlists, bounded limits and
current administrator/project checks remain strict; non-object metadata is rejected.

Ordinary preparation exposes the pending inventory, a fresh context for one job,
saving a prepared result and the read-only retained-candidate and meal-catalogue tools below. Separate
virtual-review tools keep their existing scope. There is no send, reassignment,
customer-edit or supplier-search tool.
The worker is deliberately an administrator-scoped capability for assigned-manager
contexts; ordinary manager HTTP draft permissions remain strict reply ownership.

### Retained Search3 candidates

`read_tour_candidates` is the first bounded consumer bridge for task #1141. It
reuses Search3's existing DB-first read endpoint under
`https://anytoour.ru/_preview/search3-local-candidate/data/search3-local-results-read-v1.php`.
This is the retained listing surface, not approval or deployment of the separate
Search3 product/UI release. Search3 remains the sole owner of scope compatibility,
supplier integrations, normalized offers, identity bindings, pricing and storage.
The consumer adds no adapter, refresh, retry, table, cron or paid model call.

An active current-project administrator and active requesting OAuth connection
are required before reading, and checked again after the bounded source read.
No job or customer identity is required: the tool does not open old conversations,
fabricate preparation jobs, read private history, mark messages read or change
subscriptions. Discovery keeps the existing OAuth scopes. The manual model client
still has no tools; this does not silently add a supplier call to manual generation.

Call only for an actual current request or explicit manager search. Supply exact
active catalogue departure/country names, explicit ISO date bounds, night bounds,
adults and every child's travel age. Existing `TravelDirectoryRepository` resolves
names against its canonical active catalogues; there is no guessed name/foreign-ID
join or automatic Moscow replacement. Missing names remain unresolved. Route
availability and missing trip requirements are still separate questions; this
reader does not infer them from a post, click or an old wizard. Child-age sorting
preserves duplicates. Date windows are at most21 days; night ranges are1..28 with
width at most10, matching the existing reader's contract.

For explicit meal requirements, call `read_meal_catalog` with an empty object.
It uses the same fixed endpoint and exactly
`{"action":"meal_catalog","provider":"tourvisor","scopeKey":"global"}`.
The bounded complete projection contains canonical `meal_plan_id`, `code`,
`name_ru`, `native_count` and `filter_supported`, plus the exact catalogue revision.
Labels are untrusted data. Select a supported plan from that actual catalogue;
`read_tour_candidates` accepts its `meal_plan_id` as a JSON integer in
1..9007199254740991. Numeric strings, floats, names and codes are not IDs.
The catalogue's canonical plan ID, provider/scope native token and a hotel's meal
concept remain different namespaces.

The candidate operation re-reads and validates the exact Tourvisor/global
catalogue immediately before listing, including its revision, unique IDs and
accepted native tokens. The selected plan must have exactly one supported native
token; that string is preserved without numeric conversion. Missing, unavailable,
ambiguous or whitespace-normalized mappings stop before listing with an explicit
unavailable reason. No first-alias selection or fallback removes an explicit meal.
`meal_filter` records the selected plan, exact native token and catalogue revision
separately from the request scope/digest.

Legacy `meal_id` retains its old namespace and now returns
`legacy_meal_id_unsupported` before directory/HTTP reads. Supplying it together
with `meal_plan_id` is invalid input. It is never silently reinterpreted. Omitting
both means a genuinely unfiltered meal read and makes no catalogue request; it
is not a tourist's consent to any meal. Existing Egypt/Turkish-resort working
defaults remain consultation policy, not a country-wide inference in this reader.
Optional `stars_min` is a minimum and `max_price` is an exact decimal RUB amount
for the entire stated party. No budget expansion, per-person multiplication or
fuel/fee arithmetic is performed.

All calls keep the fixed HTTPS origin, no cookies, credentials, proxy, redirects
or automatic retries, and the exact `X-Requested-With` envelope guard. That header
is not authentication. Public IPv4 resolution remains pinned to verified TLS.
An unfiltered operation has one listing POST. A filtered operation has catalogue
then listing, sharing one 5-second transfer deadline and 4MiB body budget; each
connect timeout is at most 1 second and the remaining budget. The cURL deadline
is not restarted after synchronous DNS, whose own blocking duration is not given
a stronger wall-clock guarantee. Standalone catalogue reads use the same limits.
JSON depth remains48. Catalogue projection is at most32KiB and is never silently
clipped: an oversized catalogue returns `meal_catalogue_output_too_large` with
`complete=false` and no partial list. These are unsupported-source outcomes,
not evidence that no meal plans or tours exist.

The listing response must identify the existing schema/source and exactly echo
the canonical request scope/digest with the resolved native meal token. Its
generated timestamp must be current within the stated tolerance; reading never
renews offer observation time or TTL. Wrong envelopes, non-JSON, oversized or
unavailable reads remain unknown. Access denial has a separate fixed reason;
raw error bodies are never returned. Both tools require the same active current
project administrator and requesting OAuth connection before and after reads.

The projection rechecks exact local hotel identity, dates/nights/party (including
duplicate ages), source scope, literal listing price/currency, observation/expiry
and no-booking authority. Expired, contradictory or unsupported records are
withheld and counted. Minimum category is rechecked against the accepted profile;
the source still owns meal/filter semantics. Room, meal, placement and operator
remain literal source labels or explicit nulls, not inferred equivalences.
Descriptions, photos, links, raw supplier references and arbitrary metadata are
not projected. Hotel properties and media remain uninspected. Source text is
untrusted data, never a new instruction.

Up to12 complete candidate records (default8) fit a separate32KiB response.
Distinct hotels precede a second exact stay, ordered by observed price rather
than claimed quality. Omission/rejection/source coverage are explicit. A hotel
minimum is never substituted for a particular room's price. The amount retains
its exact source stay/party and observation time; even a historically verified
listing remains `current_price_verified=false`, `refresh_required=true`, with
unknown current availability and no booking/selection authority.

The tool returns `no_retained_candidates` / `existing_live_search_required` when
the valid cache has no usable matches, and `unavailable` for source/catalogue
failures. Neither proves that the market has no tours. Useful cached candidates
can support a private comparison, with exact current price/availability and all
additional tourist constraints left for verification through the existing Search3
owner. This first slice does not start/poll live searches, mutate constructor
variants, verify send-time prices or establish natural customer/model acceptance.

MCP Events uses protocol `2026-07-28`. The event `manager_replies.pending` is scoped
to the current project. Migration 046 stores private subscriptions, OAuth connection
binding, callback verification, delivery state and bounded retry metadata.
Callbacks require HTTPS to public addresses, DNS validation at connection time,
pinned TLS hostname verification, no redirects, bounded response/time and signed
challenge verification. Deliveries use Standard Webhooks signatures; stable event IDs
survive transient retries. Payloads contain queue counts and batch identity, never
transcripts, customer identities or drafts. A receipt acknowledges delivery, not
completion of analysis. Unsubscribe, expiry, revoked account/project/grant and terminal
callback responses stop delivery. Saved results do not create a callback feedback loop.

Production deploy installs one flock-protected minute cron for
`php tools/manager_prepared_replies.php tick`, leaving unrelated cron entries intact.
Without an active authenticated subscription the tick exits in `awaiting_connection`
before scanning conversations. With a valid subscription it collects, enqueues and
delivers events; it never calls a model API. Five-to-ten-minute ChatGPT grouping is a
target after connection and delivery verification, not a guarantee of answer latency.
The available ordinary ChatGPT schedule tool permits hourly recurrence at most;
do not fabricate a subhourly schedule or a connected worker.

Every valid tick now writes a bounded private operational checkpoint beside the
canonical external diagnostic log (mode 0600, outside the application root).
It records start/finish, last successful pass, last failure and its fixed stage,
and allowlisted aggregate counters. Bootstrap failure is captured before config
loading; shutdown before completion records failure. No exception text, job IDs,
transcripts, callback URLs or credentials are stored. Diagnostic write failure
never changes processing. Missing, invalid or oversized state is explicitly
unknown; a checkpoint older than three minutes is stale. A fresh
`awaiting_connection` means the cron ran but found no authorized live subscription,
not that the queue was scanned and empty. Successful tick completion is not proof
that ChatGPT generated or a manager sent a reply.

`list_pending_replies` also returns `oauth_connection_id`: the exact internal grant
ID supplied by the HTTP owner's authenticated bearer context, including when the
queue is empty. An internal service call without that OAuth context returns null.
The value is not an app connection, task or subscription ID; request metadata and
tool arguments cannot choose it. Current admin/project/grant access is rechecked
after the inventory read. No other connection identities or credentials are
returned, and the public health projection remains unchanged. To identify an
existing hosted task's grant, read this field from that task's own actual call;
a different chat's read or a single active-subscription count is not task-binding
proof. This identifies the requesting grant only, not other consumers or permission
to revoke any grant. Tool names, arguments, scopes and event subscriptions are
unchanged.

`list_pending_replies` includes `preparation_health` under its existing active
project-admin authorization. It contains the checkpoint plus bounded read-only
subscription aggregates (active, inactive, expired, unauthorized and retrying).
Its `travel_reference` summary uses the same DB-first reader as drafts, even
with an empty queue. It exposes aggregate source, sync age, counts and explicit
coverage limits; it does not return city/country rows, filesystem paths,
credentials or transcripts. Legacy fallback reasons distinguish a missing,
inaccessible, unreadable, nonregular, oversized or malformed file. This read
neither refreshes a supplier nor repairs runtime data. An unavailable reference
is not flight unavailability.

`Restore missing MAX Search route cache` is a one-time operations workflow,
triggered only when its own restoration code changes on `main`. After successful
canonical deployment of that exact SHA, it reads the retained legacy MAX Search
cache using the existing legacy SSH credentials and the existing lead-receiver
directory discovery. It changes no legacy files. Only a validated, nonempty cache
up to 8 MiB can be installed; atomic creation refuses to replace any current file
or symlink, including a concurrent writer. Source modification time is preserved,
so historical data stays explicitly stale. Cache bytes and keys are not printed.
The workflow adds no cron, supplier call or business-data change.
It neither renews subscriptions nor sends callbacks. The same safe aggregates
are published as `manager_preparation` in production/autopilot diagnostics; their
capture time must be considered separately from the tick's own timestamps.

## Verification and rollout

Required tests cover canonical collector semantics, private cache/idempotency,
OAuth grants and revocation, callback signatures/SSRF/retry, actual HTTP boundaries
and composer races. CI also executes the queue and actual migration on isolated
MySQL. Existing browser QA covers prepared preview and manual API retry across
mobile/desktop widths. Production verification must check exact deployed SHA,
forward migrations, metadata HTTP responses, unauthorized MCP challenge and the
single installed cron. A full real subscription/analysis/save/manager-preview cycle
can be claimed only after the owner connects the plugin and the actual callback
and prepared result have been observed. No such cycle is inferred from fixtures.

If OAuth succeeds but action discovery fails, inspect `manager_mcp_discovery` in
the fresh diagnostics snapshot. The endpoint records only fixed categories for
HTTP method/status, credential-header presence/shape, discovery method, known
protocol version, stage and RPC error code in the existing private structured
log. It never records tokens, account/job IDs, origins, client strings, request
bodies or tool arguments/results. The snapshot re-allowlists the last 20 matching
records from at most 512 KiB. `missing`/`redirect_only` distinguish header delivery
from rejected credentials; authenticated discovery methods distinguish protocol
errors from authorization failures. Telemetry changes no authentication policy
or queue state. Passing a local SDK probe does not prove ChatGPT's live import.

The MCP endpoint accepts the actual `Authorization` header through PHP's direct
CGI variable, its internal-redirect variable or the server header API. A present
invalid direct value is never replaced by a fallback. The narrowly scoped
`manager/.htaccess` preserves that header for `ai-mcp.php` on Apache CGI hosts;
custom/forwarded headers are not authentication sources. Deployment also sends
one known-invalid synthetic bearer through the production host's own HTTPS
ingress and requires both a private `header_probe` observation of the effective
bearer and HTTP 401. This tests header transport without an owner token, queue
reads, grant creation or customer calls.

Rollback is a forward code revert; do not migrate down or delete business data.
Disable the dedicated cron/connection if needed. Revoke the OAuth grant to stop
callbacks immediately. Existing source messages and assignments remain unchanged.

(maximum 16 per job). The tool now declares `readOnlyHint=false` and
`idempotentHint=false`: conversation, task and read state stay unchanged, but a
private audit row is written. Packaging, source freshness and the final endpoint
administrator / OAuth audience checks precede issuance. A separated reply
surface defers issuance until its outer authorization has passed. Invalid image
packaging or failed authorization cannot expose a usable receipt. Authorization
is rechecked after issuance/lock waits and completed response packaging. A refused
response may leave an unlinked private audit row; it grants no completion access
to a revoked connection and does not prove delivery. Database or
capture unavailability leaves an explicit uncaptured result; stale jobs return
an error without the old packet. No queue, worker or provider call is added.

The immutable packet contains the exact returned normalized context, complete
context-specific instructions, base instruction revision, job/context revision,
preparation scope, latest message and returned company facts/revision. Its own
SHA-256 covers the wrapper. The image manifest hashes each complete normalized
`data:<mime>;base64,...` URL, including its byte length; MCP transports that same
MIME and base64 as image blocks. Image bytes are not retained. `text_only` is a
storage description, never a guarantee of complete source coverage. Existing
history, media, selection and truncation gaps remain visible.

Pass the exact returned `input_receipt` to `save_prepared_reply`. Do not replace
it with a newer read of the same job revision. The first pending-to-ready save
and receipt association commit in one transaction under the canonical job lock.
The receipt must match project/job/revision, authorized administrator and OAuth
connection. Identical retries preserve the original pair; a different supplied
receipt conflicts even when the proposal is identical. A retry without a receipt
preserves an already linked pair and does not replace or newly infer evidence.
Legacy saves are compatible and explicitly `not_captured` on first completion;
unavailable optional audit storage cannot lose such a save. An old identical retry
keeps the original pair and reports unknown provenance if audit readback fails; no first/latest
receipt is selected implicitly and no old row is backfilled. Job retention
cascades remove its packets and links through forward migration 082.

A receipt proves only which packet the server prepared for an authorized
response and which receipt the saving worker declared. It proves neither client
receipt/use nor the actual model, complete host/system/task/chat input or its
transformations. External model input remains `unknown`. Preview, validation and
journal reads never reconstruct that history. Automatic sending, operator modes,
provider configuration and the existing worker schedule remain unchanged.

### Hotel clarification in the current trip

The request profile can explicitly confirm one exact accepted hotel offer after
a customer's clarification. Its candidate is evidence from a retained native
web-selection inquiry, validated by the existing hotel reference owner. Finding
an earlier inquiry only offers a candidate to the manager; it never restores
its facts automatically. Names, edited offer labels and client/manager opinions
cannot establish hotel identity or become accepted research facts.

In the existing request profile, the manager reviews the latest message and
actual party/criteria, chooses the exact offer, checks the current-trip
confirmation and saves the profile. The immutable profile version retains
server-resolved offer and knowledge pins. A new message needs another review;
a new trip, newer selected offer, changed source or changed knowledge cannot
silently reuse the old confirmation. Native inquiry metadata remains separate
from ordinary text citations and cannot become a text boundary by this feature.
This finite scenario starts with an ordinary request before the selected-offer
inquiry. A conversation beginning with the inquiry and having no earlier
eligible request message still needs a separately designed boundary; it is not
silently supported by treating inquiry metadata as customer text.

Only the fresh confirmed binding can supply the hotel reference to the existing
AI draft path after a plain clarification. The profile, exact offer, accepted
facts, source dates, scopes and limitations then travel in the same normalized
input captured by existing manual/prepared evidence receipts. This does not
attest to unknown external host/model input or prove natural manager use.
Answers must address the latest question: hard requirements are suitable,
unsuitable or need clarification; preferences explain benefits and material
tradeoffs. Unknown child capacity, beach conditions or meal coverage remain
explicit checks. Hotel declarations do not verify current price, availability,
operator room/meal equivalence or operation on future travel dates.

The existing draft workflow and operator modes remain unchanged. First-cohort
demand selection, constructor consumption and automatic sending are separate
subsequent acceptance steps; none is activated by profile confirmation.

### Shared exact-offer hotel knowledge in the selection editor

Native AI selection and saved-offer reads use `ManagerHotelOfferReference` over the existing accepted hotel base. They preserve the same fact group, source records and binding revision. The internal reader accepts only a server-saved working draft version plus offer ID, or an immutable publication ID plus card index within an authorized conversation. A hotel display name or caller-supplied hotel ID is never a binding.

The manager-only `POST /manager/hotel-knowledge-api.php` requires the current session and CSRF. Supply `conversation_id` and either `{kind: "working_draft", draft_version, offer_id}` or `{kind: "publication", publication_id, card_index}`. The normal manager client may add `action: "read"`; any other action is rejected. The reader rechecks conversation access, saved selection and the session after reading. It returns no-store JSON and never changes a draft, source message, read marker or research data.

An available fact group is property evidence only. `current_trip_link`, `customer_choice_verified` and `offer_conditions_verified` remain false; price, availability, meal equivalence and future operation need their own checks. The AI current-trip confirmation keeps its separate profile/context pins. Unknown, conflicting or unavailable hotel evidence must be presented as such.

In the selection editor, save the selected option and click «Сведения об отеле». The same component runs in Manager2 and the protected standalone editor. The editor gateway routes the read through its current actor/resource guard and the canonical manager endpoint; it does not create project records while authorizing the read. Validated editor transport fields are removed before the strict saved-offer lookup. The packaged editor includes these backend dependencies in its compatibility fingerprint.

The panel displays the accepted fact group, category/facility scope, partial coverage, unknowns, source conflicts, source dates and binding revision. Reading never confirms a current trip or a supplier condition. It is disabled for unsaved/conflicting/pending changes. Changing an offer, editing, closing, suspending the account or receiving a stale version clears old facts; late replies cannot repopulate them. A visible read-only conversation may read facts without gaining editing or sending authority. Original source records remain in the response; internal research tool-citation tokens are omitted only from the presentation of source notes.

Package code and controlled UI/HTTP checks are distinct from installation and natural manager use. Import/editor ownership and the existing research queue remain unchanged.
