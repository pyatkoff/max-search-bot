# Рабочие Telegram-диалоги: экспорт истории и отдельный бизнес-бот

Поручение владельца 17.10.2026: подключить рабочие личные переписки менеджеров,
загрузить доступную историю и подготовить разбор
«запрос туриста → подборка менеджера → реакция туриста».
Трекинг подписчиков/новых обращений и отправка новых конверсий в Метрику отложены.

## Что реализовано

- Отдельный приватный архив в той же Conversation DB: migration041 создаёт
  `telegram_dialogue_connections` и `telegram_dialogue_messages`.
- Отдельный бот `@Anytourtg_bot` принимает события через
  `/telegram_archive_webhook.php`. Токен и собственный webhook secret хранятся
  вне checkout/webroot; настройки обычного `@anyru_bot` не используются.
- Migration042 добавляет реестр подключённых аккаунтов. Новое подключение
  сохраняет только метаданные аккаунта; сбор текста разрешается администратором
  после сопоставления с менеджером проекта. Разрешение проверяется под блокировкой
  реестра внутри той же транзакции, которая сохраняет сообщения.
- Обычные bot/manager conversations, очередь, прочтение, назначение, уведомления,
  отправка сообщений, lead delivery и Метрика этим архивом не изменяются.
- `business_connection`, `business_message`, `edited_business_message` и
  `deleted_business_messages` распознаются до обычного Telegram dispatcher.
  При выключенном приёме они подтверждаются без сохранения и не запускают бота.
- Ключ сообщения — проект + аккаунт менеджера + личный чат + Telegram message ID.
  Повторная загрузка не создаёт дублей; время правки и update ID защищают от
  устаревших событий. Удаление оставляет tombstone без текста, ссылок и медиа;
  старый импорт или запоздалая правка не восстанавливают удалённое содержимое.
- Сохраняются исходные времена, автор и направление, явное сопоставление с
  менеджером, текст/caption, URL (включая ссылки под отображаемым текстом),
  reply ID, признак пересылки и ссылки на вложения. Неизвестный автор остаётся
  неизвестным; сообщения business-бота не считаются человеческим ответом.
- JSON Desktop поддерживается и для отдельного чата, и для `chats.list` всего
  аккаунта. Отбор рабочих чатов явный; отсутствующий/неподдерживаемый выбранный
  чат, неоднозначное время или повреждённая запись отклоняют весь импорт.

## Импорт старой истории

В Telegram Desktop выбрать рабочие чаты и экспортировать в **JSON** с нужными
вложениями. Полнота архива ограничена доступным экспортом; удалённые или
недоступные сообщения не восстанавливаются. Файл, его вложения и выгрузку анализа
держать вне checkout/webroot/GitHub. Команды выполнять только в приватной сессии;
путь к файлу и реальные идентификаторы не публиковать в issue/Actions.

```sh
php tools/telegram_dialogue_archive.php --mode=import \
  --input=/private/telegram/result.json --account-id=100 --chat-ids=200,201 \
  --manager-id=7 --project=anytour
```

Это проверка без загрузки runtime config/БД и без вывода текстов. Сначала сверить
число выбранных чатов/сообщений, исключённые чаты и service records. После этого
та же команда с `--apply` атомарно сохраняет записи. Account/chat/manager IDs в
примере синтетические; account ID принадлежит владельцу экспортируемого аккаунта,
manager ID сопоставляется оператором с существующей учётной записью панели.

Один файл ограничен64MiB и200000 выбранных сообщений; большие экспорты разделять
по рабочим чатам/периодам. Повторяющиеся части безопасны благодаря общему ключу
сообщения. JSON нормализуется в памяти до любых записей; для большого файла
использовать достаточный CLI memory_limit и сначала выполнить dry run.

Импорт не открывает медиафайлы по экспортированным путям. Он сохраняет безопасную
относительную ссылку со статусом `not_checked`/`not_exported`; live API file IDs —
`provider_reference_only`. Скачивание, проверка байтов, распознавание голосовых,
изображений и rich-message payload пока не реализованы. Rich-only сообщения
помечаются неполными, а не выдаются за разобранный текст.

## Подключение @Anytourtg_bot через админку

Открыть [Telegram-диалоги](https://app.anytoour.ru/manager/telegram-archive.php)
после входа администратором проекта в обычный кабинет. Страница использует
канонические session/role/project/CSRF проверки менеджерского API.

1. Вставить токен созданного `@Anytourtg_bot` из BotFather в закрытое поле.
   Сервер проверяет `getMe`, точное имя и стабильный ID бота. Настройка другого
   бота или перенос webhook с чужого адреса отклоняются. Токен не возвращается
   браузеру; поле очищается после отправки. Замена токена проверяет ту же личность.
2. Включить Secretary Mode в BotFather и нажать «Проверить подключение».
   Признак `can_connect_to_business` берётся из API. Создание webhook не означает,
   что режим уже включён или что какой-либо рабочий аккаунт уже подключён.
3. В настройках рабочего Telegram-аккаунта добавить `@Anytourtg_bot` и выбрать
   рабочие личные чаты, исключив личную переписку.
4. Обновить список на странице, выбрать менеджера проекта и нажать «Включить сбор».
   До этого тексты доставленных сообщений не сохраняются. Первую проверку
   входящего/исходящего сообщения, правки и удаления выполнять после включения.
   Прежняя история добавляется через JSON-импорт ниже/выше, а не через Bot API.

Токен вводится только на HTTPS-странице приложения, не в GitHub/issue/Actions.
Конфигурация по умолчанию находится в приватном соседнем каталоге
`max-search-bot-telegram-archive` с режимами0700/0600. При необходимости доверенный
server config может задать `MAX_SEARCH_TELEGRAM_ARCHIVE_PRIVATE_DIR`; публичный
путь, symlink, чужой владелец и небезопасные права отклоняются. Сохранение атомарно,
настройка сериализована. Маркер записывается до единственного `setWebhook`; при
неизвестном исходе повторная отправка блокируется. «Проверить подключение» делает
только чтения API; первое аутентифицированное событие может подтвердить доставку
с нужным secret. Не удалять маркер и не повторять операцию вслепую.

Новый webhook получает четыре Business-типа, сохраняет pending queue и прежние
типы/параметры своего существующего подключения. Обычные сообщения новому боту
подтверждаются без запуска поиска, отправок или lead delivery. Остановка сбора
в админке и отключение бота в Telegram прекращают новые записи; уже собранные
данные не удаляются. Admin UI и status CLI не выводят токен/secret. Неподтверждённые
аккаунты видны только администратору текущего проекта.

Настройка и первая реальная приёмка требуют токена/действий владельца. По CI,
синтетическому интерфейсу или одному публичному username не объявлять бота
подключённым или пригодным для бизнеса. Трекинг и конверсии остаются отложены.

## Дополнительный приём Business-событий через прежний webhook

До активации нужны опубликованный и проверенный migration041, проверенная
идентичность бота, секрет webhook, разрешение и подключение владельца рабочего
аккаунта. В BotFather включить Business/Secretary Mode; в настройках аккаунта
подключить бота и выбрать рабочие чаты. Существующий webhook и его allowed_updates
нужно проверить: они должны включать четыре business-типа выше с сохранением
прежних типов. Не делать `drop_pending_updates` и не сбрасывать webhook.

Приватная переменная окружения `MAX_SEARCH_TELEGRAM_DIALOGUE_ARCHIVE`:

```json
{"enabled":true,"bot_key":"AnyTourArchiveBot","accounts":{"100":{"manager_id":"7","chat_ids":["200","201"]}}}
```

Значения синтетические; реальные аккаунты не коммитить. Account allowlist обязателен.
В пилоте использовать явный chat allowlist. Без `chat_ids` границы личных чатов
определяются разрешениями подключения в Telegram; такой режим активировать только
после проверки рабочего scope. Без совпадающего непустого webhook secret приём
не работает. Неизвестная connection ID вызывает ошибку для повторной доставки,
а не тихую потерю: начинать пилот с нового подключения после включения приёма.
При неполученном первоначальном connection event требуется восстановить именно
регистрацию подключения; этот код не получает доступ к старой истории через API.

Ни один аккаунт/бот/environment/webhook реально не подключается этим PR.
Публикация кода, активация приёма и подтверждение первых реальных сообщений —
отдельные проверяемые стадии. Не объявлять их завершёнными по одним тестам.

## Приватная выгрузка для разбора

```sh
php tools/telegram_dialogue_archive.php --mode=export --project=anytour \
  --account-id=100 --chat-ids=200,201 --output=/private/telegram/archive.jsonl
```

Каталог назначения должен существовать, принадлежать текущему пользователю и иметь
режим0700. Файл создаётся целиком, исключительно, с режимом0600; partial output
удаляется при ошибке, существующий файл не перезаписывается. В stdout — только
агрегат. Выгрузка идёт в согласованном read-only snapshot и использует keyset
pagination. Header фиксирует scope/ограничение покрытия, footer — количество и
SHA256 строк сообщений. Это отдельная source-schema `telegram_dialogue_archive_v1`,
не поддельный production-corpus snapshot из соседней analysis-ветки.

Первый анализ должен опираться на исходную хронологию: версия запроса до каждой
отправки подборки, предложение/объяснение и последующие сообщения туриста. Из
тишины не выводить отказ, из намерения бронировать — оплату. NLP-оценка качества,
автоматическое одобрение знаний и интеграция архива в рабочий Inbox здесь не
реализованы. Получение данных и дальнейшее использование в анализе имеют
самостоятельные цели и применимые условия обработки.

## Проверка и rollback

Required suite содержит реальные service/normalizer/dispatcher/CLI проверки на
SQLite. Отдельный PR-workflow повторяет их на native MySQL8 с каноническим SQL
migration041, включая повторный DDL, rollback и изоляцию scope. Никакой fixture
не использует рабочие идентификаторы/сообщения или production DB.

Rollback приёма: выключить приватный opt-in, затем обычный forward revert через
проектные gates. Таблицы и применённую миграцию не удалять/не переписывать; отдельно
согласовать retention/purge полученных данных. Старые диагностические privacy
границы и действующий Telegram webhook сохраняются.

Источники: [Business Bots](https://core.telegram.org/bots/features#business-bots),
[Bot API](https://core.telegram.org/bots/api),
[Desktop export](https://telegram.org/blog/export-and-more).
