## Entry and manager behavior

Each recognized repair link carries an allowlisted `as39_` + exact source post ID. The established `as39_x_battery` link remains an alias for the iPhone X battery card. A genuine contextual `bot_started` event creates one contextual reply intent in the existing event transaction, even when the same dialog is already waiting for or assigned to a manager. It preserves the exact conversation, manager ownership and existing handoff. Duplicate provider delivery reuses that event and cannot produce another send. An attempted or unknown send is not replayed. Ordinary customer messages and generic or unknown reentry remain quiet after the initial handoff greeting. The tourism manager-source policy is unchanged.

## Publication behavior

The approved batch is immutable and source-controlled, including content, navigation edges and image hashes. A real numeric channel identity must be verified against the exact public channel link and this project's bot permissions before publication. The protected project connection supplies credentials; the global AnyTour bot is never a fallback.

Repair cards are created first with their correct contextual bot buttons. Model and service pages follow; the root menu is last. Only actual provider-returned URLs populate cross-links. Final edits target only the exact messages created by this batch, with current-content checks and exact readback. Both routes must work: menu → model → repair and menu → service → repair. A published repair card points back to its model and service. The menu is pinned only after the complete verified batch is linked.

Publication operations retain a durable one-attempt intent. Changed content or connection identity cannot manufacture a new permission to repeat an uncertain send. Unknown outcomes are held for read-only reconciliation, never blindly resent. A partial run reports the exact verified count and keeps the remaining work explicit.
